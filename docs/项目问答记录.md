## 项目总览

KamaChat 是一个前后端分离的即时通信项目，目标是实现类似微信的单聊、群聊、联系人管理、文件消息以及实时通信能力。

当前仓库可以先按下面的边界理解：

| 目录 | 主要职责 |
| --- | --- |
| `cmd/kama_chat_server` | 后端服务启动入口 |
| `api/v1` | HTTP 接口控制器，负责接收请求和返回响应 |
| `internal/https_server` | HTTP/HTTPS 服务、路由和中间件 |
| `internal/service` | 业务服务层，包括聊天、GORM、Kafka、Redis 等 |
| `internal/dao` | 数据访问层和数据库初始化 |
| `internal/model` | 数据库模型和领域数据结构 |
| `internal/dto` | 请求、响应数据传输对象 |
| `pkg/auth` | JWT 等认证相关能力 |
| `pkg/constants`、`pkg/enum` | 常量和枚举 |
| `pkg/zlog` | 日志封装 |
| `web/chat-server` | Vue 前端应用 |
| `configs` | 服务配置文件 |
| `test` | 单元测试、集成测试和性能测试 |

## 第一阶段：先建立全局认识

### Q1：这个项目整体是做什么的？

**回答：**

这是一个前后端分离的即时通信系统。用户通过 Vue 前端完成登录、联系人管理、单聊和群聊等操作；后端使用 Go 提供 HTTP API，并通过 WebSocket 维持实时双向连接。消息相关流程还结合 Kafka 进行异步传输或削峰，MySQL 负责持久化业务数据，Redis 用于缓存或会话类数据。

从代码阅读角度，可以把一次用户操作拆成四层：

1. 前端页面发起 HTTP 请求或 WebSocket 消息。
2. `api/v1` 控制器解析请求、校验身份并调用业务服务。
3. `internal/service` 处理业务规则，并按需访问 MySQL、Redis、Kafka 或聊天连接。
4. 服务端返回 HTTP 响应，或通过 WebSocket 将实时消息推送给客户端。

**代码依据：**

- 后端入口：`cmd/kama_chat_server/main.go`
- HTTP 控制器：`api/v1`
- 聊天服务：`internal/service/chat`
- 数据库服务：`internal/service/gorm`
- Kafka 服务：`internal/service/kafka`
- Redis 服务：`internal/service/redis`
- 前端应用：`web/chat-server`

**面试表达：**

“这是一个 Go + Vue 的前后端分离即时通信项目。HTTP API 负责登录、联系人和群组等业务操作，WebSocket 负责实时通信，MySQL 持久化核心数据，Redis 提供缓存或会话能力，Kafka 用于消息异步处理和系统解耦。”

### Q2：数据库是怎么设计的？

**回答：**

项目使用 MySQL 保存核心业务数据，使用 GORM 作为 ORM。数据库采用“代码定义模型、启动时自动建表”的方式：`internal/dao/gorm.go` 中的 `InitDB` 建立 MySQL 连接，并对 7 个模型执行 `AutoMigrate`。当前没有看到独立的、按版本管理的 SQL migration 文件，因此它更接近 code-first 数据库设计。

#### 1. 核心表

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `user_info` | 用户基础信息和账号状态 | `id`、`uuid`、`telephone`、`password`、`status` |
| `group_info` | 群基本信息 | `uuid`、`owner_id`、`members`、`member_cnt`、`status` |
| `user_contact` | 用户的好友或群联系人关系 | `user_id`、`contact_id`、`contact_type`、`status` |
| `contact_apply` | 添加好友或申请入群记录 | `user_id`、`contact_id`、`contact_type`、`status` |
| `session` | 用户侧会话列表 | `send_id`、`receive_id`、`last_message`、`last_message_at` |
| `message` | 聊天消息 | `session_id`、`send_id`、`receive_id`、`type`、`content`、`url` |
| `file_metadata` | 上传文件的元数据 | `uuid`、`uploader_uuid`、`server_name`、`original_name`、`file_size` |

#### 2. 表之间的逻辑关系

项目主要用用户或群组的业务 `uuid` 作为跨表关联字段，而不是使用数据库自增 `id`。例如：

```text
user_info.uuid
    ├── user_contact.user_id / contact_id
    ├── contact_apply.user_id / contact_id
    ├── session.send_id / receive_id
    ├── message.send_id / receive_id
    └── file_metadata.uploader_uuid

group_info.uuid
    ├── user_contact.contact_id
    ├── contact_apply.contact_id
    ├── session.receive_id
    └── message.receive_id
```

这些是业务层逻辑关联。模型中没有显式的 GORM `foreignKey` 或数据库外键约束，数据一致性主要由 `internal/service/gorm` 中的业务代码保证。

#### 3. 群成员的特殊设计

`group_info.members` 是 JSON 字段，保存成员 UUID 数组；`member_cnt` 保存成员数量。创建、加入、退出和移除成员时，服务层会读取 JSON、修改数组，再保存回群表。同时，`user_contact` 还会保存用户到群的联系人记录和状态。

这样设计的优点是读取一个群的成员列表比较直接，开发成本低；缺点是成员增删需要改写整段 JSON，难以对单个成员建立数据库约束或高效查询。更规范、适合大规模群聊的方案通常会拆出 `group_member` 关系表，例如 `group_id + user_id + role + status`。

#### 4. 消息和会话设计

`message` 保存消息明细，支持文本、语音、文件和通话等类型。`type` 区分消息类型，`content` 保存文本或业务内容，`url` 负责文件等资源地址，`send_id` 和 `receive_id` 分别表示发送方和接收方。

`session` 更像用户侧的会话列表索引，而不是消息明细表。它保存最近一条消息、最近时间以及接收方名称和头像，因此打开会话列表时不需要扫描全部消息。代价是名称、头像和最近消息属于冗余字段，用户资料变化时需要同步更新。

#### 5. 索引、删除和文件

- 大多数表使用自增 `id` 作为主键，业务 `uuid` 建立唯一索引。
- 用户手机号、用户状态、创建时间、联系人双方 ID、会话双方 ID、消息会话 ID 等字段建立了索引，服务层的查询会使用这些字段。
- 用户、群组、联系人、申请、会话和文件元数据使用 `gorm.DeletedAt` 实现软删除；普通 GORM 查询默认不会返回已软删除数据，需要时使用 `Unscoped()`。
- 文件本体保存在服务器文件目录，`file_metadata` 只保存文件名、原始名、MIME 类型、大小、上传者等元数据，避免把大文件直接放进 MySQL。

**代码依据：**

- 数据库连接和自动建表：[internal/dao/gorm.go](../internal/dao/gorm.go)
- 表模型：[internal/model/user_info.go](../internal/model/user_info.go)、[internal/model/group_info.go](../internal/model/group_info.go)、[internal/model/user_contact.go](../internal/model/user_contact.go)、[internal/model/contact_apply.go](../internal/model/contact_apply.go)、[internal/model/session.go](../internal/model/session.go)、[internal/model/message.go](../internal/model/message.go)、[internal/model/file_metadata.go](../internal/model/file_metadata.go)

**面试表达：**

### Q3：介绍一下项目，重点讲讲亮点和难点

**回答：**

KamaChat 是一个 Go + Vue 的前后端分离即时通信系统，支持用户注册登录、好友和群组管理、单聊、群聊、文件消息、语音视频通话消息以及后台管理。后端使用 Gin 提供 HTTP API，使用 WebSocket 提供实时双向通信，MySQL 保存核心业务数据，Redis 用于消息和会话缓存，Kafka 用于消息削峰和异步处理。

从请求链路看，HTTP API 负责登录、联系人、群组、会话和文件上传等业务；WebSocket 负责建立用户在线连接和实时收发消息；消息进入聊天路由后，会经过会话级顺序控制、消息持久化、在线用户推送和缓存更新。

#### 项目亮点

**1. Hybrid 消息路由。**

项目不是固定只使用 Channel 或 Kafka，而是提供 `channel`、`kafka` 和 `hybrid` 三种模式。Hybrid 模式下，正常负载优先走内存 Channel，背压检测器发现 Channel 长时间超过高水位后，把消息分流到 Kafka；拥塞恢复后再切回 Channel。一个会话一旦切到 Kafka，在恢复前保持 Kafka 路由粘性，避免同一个会话同时走两条链路造成乱序。

**2. 会话级有序处理。**

Hybrid 路由会为每个 `session_id` 分配递增序号，`SessionRouter` 为每个会话维护独立队列。同一个会话中的消息串行处理，乱序消息先进入缓冲区，重复或过期序号会被丢弃；不同会话之间可以并行处理。这同时解决了消息顺序和整体吞吐之间的矛盾。

**3. Kafka offset 与持久化结果绑定。**

Kafka 消费端使用 `FetchMessage` 获取消息，经过 `SessionRouter` 和 `MessageProcessor` 处理，并在消息持久化成功后才提交 offset。这样进程在持久化前崩溃时，消息可以重新消费，而不是因为提前提交 offset 导致消息丢失。

**4. 消息持久化和实时推送解耦。**

消息先写入消息批处理器，再推送给在线用户。批处理器默认累积 50 条或等待 10ms 后批量写入 MySQL，并对失败批次重试。WebSocket 客户端使用有界发送队列，慢客户端只会在有限时间内阻塞，不会长时间占用全局客户端锁或拖慢其他会话。

**5. 文件上传具备基本安全闭环。**

上传接口限制文件大小和允许的 MIME 类型，同时读取文件头进行内容检测，服务端重新生成文件名，拒绝可执行扩展名。文件下载需要 JWT，并通过文件元数据、发送/接收关系或群成员关系进行归属校验。文件落盘失败或元数据写入失败时，代码会尝试清理已经落盘的文件。

**6. 具备一定的可观测性和压测基础。**

项目暴露 `/metrics` 接口，统计 Channel/Kafka 路由数量、投递队列超时、会话队列超时、处理失败和批量写入失败等指标；`test/performance` 还提供 WebSocket 压测程序，用于观察连接数、吞吐和延迟。

#### 项目难点

**1. 多条消息链路下如何保证顺序。**

Channel 延迟低但容量有限，Kafka 可以削峰但引入异步消费和 offset 管理。两条链路并存时，最容易出现同一会话的消息先后顺序变化。项目通过 `session_id` 作为 Kafka key、会话粘性路由和 `SessionRouter` 序号缓冲共同解决这个问题。

**2. 如何定义“消息处理成功”。**

实时推送成功不等于消息已经持久化，写入数据库成功也不等于对端已经在线收到。因此代码把消息状态、批量写入结果、Kafka offset 和 WebSocket 投递分别处理：Kafka 路径以持久化完成作为 offset 提交边界，WebSocket 投递使用超时和计数器记录慢客户端，历史消息可以通过数据库恢复。

**3. 高并发下的背压和慢客户端。**

消息生产速度可能超过 Channel、Kafka、数据库或某个客户端的处理速度。项目使用有界队列、超时、背压检测、Kafka 分流、批量写入和异步 Redis 更新，尽量避免一个慢客户端阻塞全部用户。难点在于不能简单地无限扩大缓冲区，否则只是把问题转化为内存增长和更高尾延迟。

**4. 群聊扇出和并发安全。**

一条群消息需要读取成员列表，再向多个在线客户端投递。实现中先在锁内复制客户端引用，释放锁后再逐个写入发送队列，避免在锁内等待慢客户端；同时还要处理成员退出、群解散、会话删除和缓存失效之间的一致性。

**5. 多组件生命周期管理。**

服务同时运行 HTTP/TLS、WebSocket 读写协程、Channel 路由器、Kafka 消费协程、批量写入协程和缓存 worker。启动顺序、异常重试、通道关闭、最终刷盘和优雅退出都需要明确，否则容易出现 goroutine 泄漏、重复消费或尾部消息未落库。

#### 需要诚实说明的边界

当前在线客户端、Hybrid 路由状态和部分会话状态主要保存在进程内存中，因此系统更接近单实例或单节点实现。若扩展到多实例，需要增加共享在线状态、分布式消息路由、跨实例 WebSocket 投递以及更明确的 Kafka 分区和消费组方案。另外，群成员使用 JSON 保存，适合当前规模，但大规模群聊应改为独立的 `group_member` 关系表。

**面试表达：**

“KamaChat 是一个 Go + Vue 的即时通信项目。HTTP API 负责账号、联系人、群组和文件业务，WebSocket 负责实时通信，MySQL 持久化，Redis 做缓存，Kafka 负责削峰和异步处理。项目比较有特点的是 Hybrid 消息路由：正常情况下走低延迟的 Channel，Channel 持续高负载时按会话分流到 Kafka，并通过 Kafka key、会话粘性和 SessionRouter 保证同一会话有序。消息处理还把持久化、实时推送和缓存更新解耦，Kafka 只有在消息持久化成功后才提交 offset。项目的难点主要是多链路下的顺序和可靠性、慢客户端背压、群聊扇出以及多个 goroutine 和中间件的生命周期管理。”

### Q4：User 表是怎么设计的？有哪些核心字段？是否建立了索引？

**回答：**

用户表对应模型 `model.UserInfo`，表名是 `user_info`。它同时保存账号身份、个人资料、登录状态和管理员权限。设计上使用自增 `id` 作为数据库主键，使用业务 `uuid` 作为对外和跨表关联的用户 ID。

#### 核心字段

| 字段 | 类型/约束 | 作用 |
| --- | --- | --- |
| `id` | `int64`，主键 | 数据库内部主键，便于 InnoDB 组织记录 |
| `uuid` | `char(20)`，唯一索引 | 业务用户 ID，好友、群组、会话和消息都通过它关联用户 |
| `telephone` | `char(11)`，可空 | 可选资料字段，不参与认证 |
| `password` | `varchar(60)`，非空 | 保存 bcrypt 哈希后的密码，不应保存明文 |
| `nickname` | `varchar(20)`，非空 | 用户昵称 |
| `email` | `varchar(254)`，非空，唯一索引 | 登录账号和邮箱验证码凭证 |
| `avatar` | `char(255)`，非空，有默认值 | 头像地址 |
| `gender` | `int8` | 性别枚举值 |
| `signature` | `varchar(100)` | 个性签名 |
| `birthday` | `char(8)` | 生日 |
| `is_admin` | `int8`，非空 | 是否为管理员 |
| `status` | `int8`，非空 | 用户状态，例如正常、禁用 |
| `created_at` | `datetime`，非空 | 创建时间 |
| `deleted_at` | `datetime` | GORM 软删除时间 |
| `last_online_at` / `last_offline_at` | 可空时间 | 最近上线和下线时间，使用 `sql.NullTime` 表示可能为空 |

#### 已建立的索引

模型标签中明确建立了以下索引：

- `id`：`primaryKey`，主键索引。
- `uuid`：`uniqueIndex`，唯一索引，保证业务 ID 不重复。
- `email`：`uniqueIndex`，唯一索引，登录和注册检查会按邮箱查询。
- `telephone`：`index`，普通索引，仅用于资料展示和联系人功能。
- `created_at`：`index`，便于按创建时间查询或排序。
- `status`：`index`，便于筛选正常用户、禁用用户等状态。

`email`、`nickname`、`is_admin`、`last_online_at` 和 `last_offline_at` 在当前模型中没有显式索引。`deleted_at` 虽然用于 GORM 软删除条件，但 `UserInfo` 的标签中没有像部分其他模型那样明确写 `index`，因此不能把它说成已经建立了索引。

#### 一个重要的设计细节

邮箱有唯一索引，保证每个邮箱只能注册一个账号。注册时，`user_info_service.go` 会先通过 `email` 查询用户，确认不存在后再插入；数据库层的唯一索引提供了双重保障，防止并发注册产生重复账号。

密码安全方面，注册流程使用 bcrypt 哈希后写入 `password`；登录时按邮箱查询用户，再校验密码。用户默认使用 GORM 的软删除机制，普通查询会自动排除已经删除的用户，管理员查询可以使用 `Unscoped()` 查看全部记录。

**面试表达：**

### Q5：Kafka 消费失败怎么处理？如何保证消息不丢失？

**回答：**

项目采用“手动提交 offset + 处理成功后提交”的策略。Kafka 消费者先使用 `FetchMessage` 获取消息，不开启自动提交；消息交给 `SessionRouter` 和 `MessageProcessor` 处理，只有消息成功完成持久化后，才调用 `CommitMessages` 提交 offset。

#### 消费失败时的处理流程

1. **Kafka 读取失败：** `FetchMessage` 出错时使用指数退避重试，重试次数达到上限后会重置计数器并继续等待重试。消费者 goroutine 发生 panic 时，也会按递增等待时间重新进入消费循环。
2. **业务处理失败：** 消息进入 `SessionRouter.EnqueueMessageAndWait`，处理失败不会提交 offset，而是等待一段时间后重新处理当前 Kafka record。代码不会继续提交后续 offset，避免一次失败被后续提交覆盖。
3. **数据库批量写入失败：** `MessageBatchWriter` 默认按 50 条或 10ms 批量写入 MySQL，单批失败最多重试 3 次；如果最终失败，会通过 `done` 通道把错误返回给 Kafka 消费路径，因此该消息不会被确认。
4. **offset 提交失败：** 即使业务处理已经成功，只要 `CommitMessages` 失败，也会重试当前 offset。这样可能造成消息重复处理，但不会因为提交失败而直接跳过消息。

#### 项目目前如何降低消息丢失风险

- Kafka Reader 设置 `CommitInterval: 0`，由业务代码手动提交 offset。
- 消费端使用 `FetchMessage`，而不是读取后自动提交。
- Kafka 处理超时时间为 2 分钟，处理成功后才允许提交 offset。
- Kafka Producer 使用 `RequiredAcks: kafka.RequireAll`，等待副本确认后才认为写入成功。
- 同一会话使用 `session_id` 作为 Kafka key，并由 `SessionRouter` 保证顺序。
- 消息批量落库失败会重试，并通过指标记录 `process_failures`、`kafka_commit_failures` 和 `batch_flush_errors`。

#### 需要准确说明：当前不是绝对的“消息零丢失”

面试时不能简单说“项目已经保证消息绝不丢失”，因为当前实现还有几个边界：

1. **Channel 路径没有等待落库结果。** `MessageProcessor.ProcessMessage` 的普通路径把消息交给 `MessageBatch.Enqueue` 后立即返回，只有 Kafka 路径调用 `ProcessMessageAndWait` 并等待 `done`。如果 Channel 模式下进程在批量刷盘前崩溃，内存中的消息可能丢失。
2. **批量写入三次失败后会报告失败。** `MessageBatchWriter` 最终会把错误返回给等待者，但批次已经从内存 buffer 中取出；Kafka 路径可以依靠未提交 offset 重试，Channel 路径没有同等的持久化确认和恢复机制。
3. **生产者发送失败目前主要返回错误或记录日志。** Hybrid 路径会尝试回退到 Channel，但如果 Kafka 已经写入成功后客户端没有收到响应，重试可能造成重复；纯 Kafka 路径的写入失败主要记录日志，没有独立的生产者重试队列或 Outbox。
4. **Topic 创建配置是单副本。** `CreateTopic` 使用 `ReplicationFactor: 1`，即使 Writer 设置 `RequireAll`，也只能等待唯一副本确认。单 Broker 故障时没有副本可以恢复，生产环境应该使用多 Broker、多副本和合适的 `min.insync.replicas`。
5. **当前缺少死信队列和人工介入机制。** 业务数据持续非法或数据库长期不可用时，当前消费者会持续重试并阻塞当前消费位置；生产系统通常需要重试主题、死信主题、告警和可重放工具。
6. **重试需要幂等设计。** offset 提交失败或消费者重启可能导致同一消息再次处理。消息 UUID 有唯一索引是基础保护，但更完整的方案还应使用消息 UUID 幂等表、唯一约束或状态机，避免重复写入会话、缓存和推送副作用。

#### 更完整的可靠性方案

如果要把它提升为更可靠的生产级实现，可以按下面的顺序改进：

- 统一 Channel 和 Kafka 路径：消息进入处理链后都等待数据库持久化确认，再返回成功。
- 使用消息 UUID 做幂等键，在消费处理前检查或通过唯一约束保证重复消费不会重复创建业务记录。
- 引入 Outbox 或可靠生产者：先在本地事务中写入待发送记录，再由后台任务投递 Kafka，并记录发送状态。
- Kafka 使用多副本，配置 `acks=all`、`min.insync.replicas` 和合理的重试/幂等生产者参数。
- 为持续失败的消息设计重试 Topic、死信 Topic、告警和人工重放流程。
- 监控 Consumer Lag、数据库持久化数量、Kafka 消费数量、WebSocket 收到数量、重复数和序号缺口。
- 优雅停机时停止接收新消息，等待消费者和批量写入器完成，并对未完成消息进行可恢复处理。

**面试表达：**

“Kafka 消费端使用手动提交 offset 的方式，先 FetchMessage，再经过会话队列和消息处理器完成数据库持久化，只有处理成功后才 CommitMessages。读取失败、业务处理失败和 offset 提交失败都会重试，处理失败时不会提交 offset，所以进程重启后消息可以重新消费。Kafka 写入端使用 RequireAll 等待副本确认。需要说明的是，当前实现对 Kafka 路径提供了较强的至少一次处理语义，但还不是端到端绝对不丢：Channel 路径没有等待批量落库，Topic 当前是单副本，也缺少 Outbox、死信队列和完整幂等机制。生产环境还需要补齐这些能力。”

### Q6：WebSocket 是怎么工作的？

**回答：**

WebSocket 在项目中负责维持客户端和服务端之间的长连接，实现消息的实时双向传输。HTTP API 负责登录、联系人、群组和历史消息查询，WebSocket 负责在线状态下的消息发送和推送。

#### 1. 连接建立和鉴权

后端在 `internal/https_server/https_server.go` 注册 `GET /wss` 路由。前端登录成功拿到 JWT 后，使用 `wss://127.0.0.1:8000/wss?token=<JWT>` 创建连接。服务端在 `WsLogin` 中完成以下步骤：

1. 从 query 参数 `token` 获取 JWT；没有 query 参数时兼容读取 `Authorization: Bearer <token>`。
2. 调用 `auth.ParseToken` 验证签名和有效期。
3. 从 JWT claims 中取出 `uuid`，不信任 URL 中额外传入的 `client_id`。
4. 调用 Gorilla WebSocket 的 `Upgrade` 将 HTTP 连接升级为 WebSocket 连接。
5. 创建 `Client` 对象，注册到当前消息模式对应的聊天服务，并启动读写协程。

服务通过 `RunTLS` 启动，因此前端使用的是 `wss`。认证发生在 WebSocket 升级之前，认证失败时不会建立长连接。

#### 2. 一个连接对应的核心对象

`Client` 主要包含：

| 字段 | 作用 |
| --- | --- |
| `Conn` | Gorilla WebSocket 连接对象 |
| `Uuid` | JWT 解析出的用户业务 ID |
| `SendTo` | 发送给服务端的通道，当前主要是历史结构保留 |
| `SendBack` | 服务端推送给该客户端的有界队列，容量为 4096 |
| `done` | 连接关闭通知通道 |
| `closeOnce` | 保证多个关闭路径下只执行一次关闭逻辑 |

服务端维护 `map[string]*Client`，以用户 UUID 找到在线连接。读写客户端映射时使用 `RWMutex`，避免并发登录、退出和消息推送访问 map 产生数据竞争。

#### 3. 读协程：客户端消息进入后端

每个客户端启动一个 `Read` 协程，循环调用 `Conn.ReadMessage()`。收到 JSON 后，根据配置的 `messageMode` 进入不同路径：

```text
浏览器 WebSocket.send(JSON)
        │
        ▼
Client.Read
        ├── channel  -> ChatServer.Transmit
        ├── hybrid   -> HybridChatRouter.SendMessage
        └── kafka    -> Kafka ChatWriter
```

Hybrid 模式会先从消息中提取 `session_id`，分配会话序号，然后根据 Channel 背压状态决定走内存 Channel 还是 Kafka。进入 Kafka 的会话在恢复前保持 Kafka 路由粘性，以维持同一会话的顺序。

消息进入后端后，`SessionRouter` 为每个会话维护独立队列，`MessageProcessor` 负责解析文本、文件、语音/视频通话消息，写入消息表，并根据接收者是用户还是群组进行推送。

#### 4. 写协程：后端消息推送到客户端

服务端不会让业务 goroutine 直接操作每个 WebSocket 连接，而是先把 `MessageBack` 放入目标客户端的 `SendBack` 队列。每个客户端只有一个 `Write` 协程从队列取消息并调用 `Conn.WriteMessage()`。

单聊时，消息会投递给接收者和发送者自己，形成对发送方的回显；群聊时，服务端读取群成员列表，复制当前在线成员的连接引用，然后在释放客户端 map 的读锁后逐个入队。这样慢客户端不会长时间占用全局锁。

`SendBack` 是有界队列，入队最多等待 500ms。队列满或连接已关闭时返回错误并增加指标，不会无限阻塞当前会话处理。因为消息已经先持久化，离线用户后续可以通过历史消息接口恢复。

```text
MessageProcessor
        │
        ├── 创建 MessageBack
        ├── 找到目标 Client
        └── Client.EnqueueDelivery
                    │
                    ▼
              Client.SendBack
                    │
                    ▼
              Client.Write
                    │
                    ▼
              WebSocket.Conn.WriteMessage
```

写协程发送成功后，会把消息 UUID 放入投递状态队列，由后台 worker 批量把 `message.status` 更新为已发送状态。

#### 5. 连接断开和退出

当 `ReadMessage` 返回错误时，服务端认为连接已经断开：调用 `Close` 关闭 `done` 和底层连接，再从当前模式的 `Clients` map 中移除用户。显式退出时，服务端通过 Logout 通道删除连接并调用 `client.Close()`。

`done` 让写协程及时退出，`closeOnce` 防止读错误、显式退出和其他清理路径同时关闭同一个 channel 引发 panic。

#### 6. 前端的使用方式

前端把 WebSocket 保存在 Vuex 的 `store.state.socket` 中。登录成功后创建连接，设置 `onopen`、`onmessage`、`onclose` 和 `onerror` 回调；进入具体聊天页面时，页面设置自己的 `onmessage`，解析服务端 JSON，并根据 `receive_id`、`send_id` 和当前会话过滤消息。发送文本、文件和通话信令时，直接调用 `socket.send(JSON.stringify(request))`。

**面试表达：**

“项目通过 `/wss` 建立 WebSocket 长连接，连接握手前校验 JWT，并使用 JWT 中的 UUID 作为客户端身份。每个连接对应一个 Client，服务端为它启动一个读协程和一个写协程：读协程负责接收 JSON 并把消息交给 Channel、Kafka 或 Hybrid 路由，写协程只从有界 SendBack 队列读取消息并写回浏览器。业务层通过客户端 UUID 找到在线连接，消息先完成持久化，再投递给发送方、接收方或群成员。断开时通过 done 通道和 closeOnce 做并发清理。这样 WebSocket 负责实时传输，消息顺序、持久化和削峰则由 SessionRouter、MySQL、Redis 和 Kafka 等组件负责。”

#### 需要注意的实现边界

- 当前代码没有看到完整的心跳 Ping/Pong、读写 deadline 和自动重连机制；生产环境需要处理 NAT、网络抖动和半开连接。
- `Upgrader.CheckOrigin` 当前直接返回 `true`，生产环境应限制可信 Origin。
- 所有 WebSocket 写操作最好统一进入同一个写协程；欢迎语、退出语等控制消息也应通过 `SendBack` 入队，避免业务 goroutine 与 `Client.Write` 并发调用 `WriteMessage`。
- 当前在线连接保存在单进程内存中，多实例部署时需要共享在线状态或通过网关/消息总线完成跨实例投递。

### Q7：用户在新设备登录后，拉取 Session 列表和点击 Session 加载聊天记录的全过程是什么？

**回答：**

这两个流程实际上由两条链路组成：

- **Session 列表：** 登录后通过带 JWT 的 HTTP API 拉取，分为用户会话和群聊会话两个接口。
- **聊天记录：** 点击列表项后进入聊天页面，先获取联系人详情和会话 UUID，再通过单聊或群聊历史消息接口加载记录。

WebSocket 负责后续的实时消息推送，但不是历史 Session 列表和聊天记录的主要查询通道。

#### 一、新设备登录后的准备阶段

1. 前端调用 `POST /login`，提交手机号和密码。
2. 后端查询 `user_info`，校验密码和用户状态，返回用户资料以及 JWT。
3. 前端把用户资料和 JWT 保存到 Vuex，同时写入 `sessionStorage`。
4. 前端使用 JWT 创建 `wss://.../wss?token=<JWT>` WebSocket 连接。
5. 后端校验 JWT，从 claims 中取出当前用户 UUID，创建 `Client` 并放入在线连接 Map。
6. 登录页跳转到 `/chat/sessionlist`。

新设备没有旧设备的前端 Session 列表缓存，因此列表必须从服务端重新获取。当前页面是用户展开“用户”或“群聊”菜单时才触发对应的拉取函数，不是登录接口直接返回 Session 列表。

#### 二、拉取用户 Session 列表

前端 `SessionList.vue` 展开用户会话菜单后，发送：

```http
POST /session/getUserSessionList
Authorization: Bearer <JWT>
Content-Type: application/json
```

请求体中会带上：

```json
{
  "owner_id": "U..."
}
```

但后端 `GetUserSessionList` 不信任请求体中的 `owner_id`，而是从 JWT 鉴权中间件写入的 context 获取当前用户 UUID，再调用 `SessionService.GetUserSessionList(currentUuid)`。

服务层执行缓存优先查询：

```text
Redis: session_list_<当前用户 UUID>
        │
        ├── 命中：JSON 反序列化，直接返回
        │
        └── 未命中：查询 MySQL session 表
                         │
                         ├── WHERE send_id = 当前用户 UUID
                         ├── ORDER BY created_at DESC
                         └── 只保留 receive_id 以 U 开头的记录
```

数据库中的 `session` 记录是用户侧会话记录。当前实现查询当前用户作为 `send_id` 的记录，GORM 会自动排除软删除记录。服务层把模型转换成：

```json
{
  "session_id": "S...",
  "avatar": "...",
  "user_id": "U...",
  "user_name": "..."
}
```

如果是数据库回源，服务层会将结果序列化后写入 `session_list_<uuid>` Redis key，并设置过期时间；然后返回给控制器。控制器统一包装成 `{code, message, data}`，前端把相对头像地址拼成完整后端 URL，保存到 `userSessionList`，由 Vue 渲染列表。

#### 三、拉取群聊 Session 列表

用户展开群聊菜单后，流程与用户 Session 基本相同，但接口和缓存 key 不同：

```http
POST /session/getGroupSessionList
Authorization: Bearer <JWT>
```

服务层使用：

```text
Redis: group_session_list_<当前用户 UUID>
MySQL: WHERE send_id = 当前用户 UUID ORDER BY created_at DESC
过滤：receive_id 以 G 开头
```

响应结构是：

```json
{
  "session_id": "S...",
  "avatar": "...",
  "group_id": "G...",
  "group_name": "..."
}
```

用户和群聊列表虽然复用同一张 `session` 表，但通过 `receive_id` 的前缀区分：`U` 表示用户，`G` 表示群组。

#### 四、点击用户或群 Session

前端点击 Session 后，并没有直接使用响应中的 `session_id`，而是使用 `user_id` 或 `group_id` 跳转：

```text
用户 Session -> /chat/<user_id>
群聊 Session -> /chat/<group_id>
```

进入 `ContactChat.vue` 后，页面按顺序执行：

1. 调用 `/contact/getContactInfo` 获取对方用户或群组详情。
2. 调用 `/session/openSession`，提交当前用户和目标用户/群组 ID。
3. 后端把 `send_id` 强制替换为 JWT 中的当前用户 UUID。
4. 服务层查询或创建当前用户到目标对象的 Session，并返回 `session.uuid`。
5. 前端将返回值保存到 `data.sessionId`，后续发送文本、文件和通话信令时使用它。

`OpenSession` 的逻辑是：

```text
查找当前用户 -> 目标对象的 session
        │
        ├── 找到：返回已有 session.uuid
        │
        └── 找不到：校验目标用户/群组状态
                         │
                         ├── 用户正常或群组正常：创建 session
                         └── 禁用或不存在：返回错误
```

创建 Session 时会把接收方昵称/群名和头像冗余保存到 `session.receive_name`、`session.avatar`，这样列表查询不需要每次再关联用户表或群组表。创建后会删除当前用户对应的 Session 列表缓存。

#### 五、点击用户 Session 后加载单聊记录

如果路由 ID 以 `U` 开头，前端调用：

```http
POST /message/getMessageList
Authorization: Bearer <JWT>
```

请求体大致是：

```json
{
  "user_one_id": "U_current",
  "user_two_id": "U_target"
}
```

后端控制器会覆盖 `user_one_id`，强制使用 JWT 中的当前用户，避免客户端伪造查询身份。然后进行权限校验：

- 不允许查询自己和自己的聊天记录。
- `user_contact` 中必须存在任意方向的好友关系。
- `contact_type = 0`，表示用户联系人。
- `status = 0`，表示正常关系。
- `deleted_at IS NULL`，排除软删除、拉黑或删除状态。

权限通过后进入 `MessageService.GetMessageList`：

```text
Redis: message_list_<当前用户>_<目标用户>
        │
        ├── 命中：JSON 反序列化并返回
        │
        └── 未命中：查询 MySQL message 表
                 WHERE (send_id = 当前用户 AND receive_id = 目标用户)
                    OR (send_id = 目标用户 AND receive_id = 当前用户)
                 ORDER BY created_at ASC
```

查询结果会转换为消息响应，包括发送者、接收者、消息类型、文本内容、文件 URL、文件类型、文件名、文件大小和创建时间。前端补全头像 URL，把结果放入 `data.messageList`，再滚动到消息底部。

#### 六、点击群聊 Session 后加载群聊记录

如果路由 ID 以 `G` 开头，前端调用：

```http
POST /message/getGroupMessageList
Authorization: Bearer <JWT>
```

请求体是：

```json
{
  "group_id": "G..."
}
```

控制器先校验当前用户是否为有效群成员：

- `user_contact.user_id = 当前用户`。
- `user_contact.contact_id = 群 UUID`。
- `contact_type = 1`，表示群联系人。
- `status = 0`，表示正常成员状态。
- `deleted_at IS NULL`，排除退出、被踢和删除状态。

通过校验后，服务层查询：

```text
Redis: group_messagelist_<群 UUID>
        │
        ├── 命中：JSON 反序列化并返回
        │
        └── 未命中：查询 MySQL message 表
                 WHERE receive_id = 群 UUID
                 ORDER BY created_at ASC
```

前端收到响应后同样补全头像 URL，写入 `data.messageList` 并滚动到底部。

#### 七、历史记录加载后的实时更新

历史消息通过 HTTP 返回后，聊天页面会覆盖当前 WebSocket 的 `onmessage`。后续实时消息从 WebSocket 到达时，前端根据 `receive_id`、`send_id` 和当前路由会话判断是否追加到当前 `messageList`：

- 当前单聊的接收消息：追加。
- 当前群聊的群消息：追加。
- 当前用户自己的消息回显：追加。
- 其他会话的消息：当前页面不展示，切换会话或刷新时再通过历史消息接口加载。

因此完整链路可以概括为：

```text
新设备登录
  -> 保存 JWT + 建立 WebSocket
  -> 进入 SessionList
  -> 展开用户/群菜单
  -> Redis 命中或 MySQL 回源
  -> 点击目标 ID
  -> 获取联系人详情
  -> openSession 获取/创建 session.uuid
  -> 权限校验
  -> Redis 命中或 MySQL 查询历史消息
  -> 前端渲染历史消息
  -> WebSocket 持续追加实时消息
```

#### 当前实现中值得注意的问题

- Session 列表接口接收 `owner_id`，但后端实际使用 JWT 用户 ID，这是正确的安全做法；前端传入字段只是冗余。
- Session 列表返回了 `session_id`，但点击时前端使用的是 `user_id` 或 `group_id`，之后又调用 `openSession` 重新获取 Session ID，存在一次额外查询。
- `GetMessageList` 和 `GetGroupMessageList` 中的 Redis 回源写入代码目前被注释，实时消息处理器可能会异步更新缓存，因此首次新设备加载通常应以 MySQL 为事实来源。
- `OpenSession` 的缓存辅助函数 `GetKeyWithPrefixNilIsErr` 返回的是匹配到的 Redis key 名称，而不是 key 对应的 value；同时写入 Session 缓存的代码被注释。当前主要依赖 MySQL 回源，若启用该缓存逻辑需要修正为直接按完整 key 读取值。
- 消息接口当前一次性加载完整会话历史，没有分页参数；历史消息很多时会造成较大的 DB、Redis 和网络开销，生产环境应改为按时间或消息 ID 分页。

**面试表达：**

“新设备登录后，前端保存 JWT、建立 WebSocket，然后进入 Session 页面。展开用户或群聊菜单时，前端调用带 JWT 的 Session 列表接口，后端忽略请求体中的 owner_id，直接从 JWT 获取当前用户身份。服务层先查 Redis，未命中则查询当前用户 send_id 对应的 session 表记录，按创建时间倒序排列，再按 receive_id 前缀区分用户和群聊，并回写缓存。点击 Session 后，前端用目标用户 ID 或群 ID进入聊天页，先获取联系人详情，再调用 openSession 获取或创建当前用户到目标对象的 session.uuid。之后单聊会校验好友关系并查询双方消息，群聊会校验群成员关系并查询 receive_id 对应的群消息；历史消息优先查 Redis，未命中回源 MySQL，按 created_at 正序返回。历史记录显示后，新的消息继续通过 WebSocket 推送并追加到当前会话。”

### Q8：用户密码是否做了加密存储？登录请求过来后如何校验？

**回答：**

密码不是可逆加密，而是使用 bcrypt 做单向哈希存储。项目使用 `bcrypt.DefaultCost`，生成的 bcrypt 字符串固定约 60 个字符，数据库字段 `user_info.password` 定义为 `varchar(60)`。即使数据库泄露，也不能直接从字段还原原始密码；登录时只能把用户输入的密码拿来做哈希校验。

#### 一、注册时的密码处理

注册请求到达 `POST /register` 后，服务层大致按以下顺序处理：

1. 邮箱规范化（TrimSpace + 转小写），校验邮箱格式。
2. 从 Redis 读取 `auth_code_email_<email>` 对应的邮箱验证码并校验，成功后删除验证码（一次性消费）。
3. 查询邮箱是否已经注册（数据库唯一索引 + Service 层双重保证）。
4. 调用 `auth.HashPassword(registerReq.Password)`，内部执行 `bcrypt.GenerateFromPassword`。
5. 将返回的 bcrypt 哈希写入 `UserInfo.Password`，不会把原始密码作为正常字段保存。
6. 创建用户记录（`telephone` 为空），并签发 JWT 返回给前端。

bcrypt 每次生成哈希都会使用随机 salt，因此即使两个用户使用相同密码，数据库中的哈希也不会相同。登录时不应该直接比较哈希字符串，而应该使用 bcrypt 的校验函数。

#### 二、密码登录校验流程

前端登录页通过 HTTPS 调用：

```http
POST /login
Content-Type: application/json
```

请求体为：

```json
{
  "email": "user@example.com",
  "password": "用户输入的密码"
}
```

后端流程是：

```text
Login Controller
      │
      ▼
UserInfoService.Login
      │
      ├── 按 email 查询 user_info（规范化后）
      ├── 用户不存在 -> 返回登录失败
      ├── bcrypt 校验 password
      ├── 校验失败 -> 返回密码错误
      └── 校验成功 -> 生成 JWT 并返回用户信息
```

具体步骤如下：

1. Controller 使用 `BindJSON` 解析邮箱和密码。
2. Service 对邮箱执行 `TrimSpace` 和 `ToLower` 规范化，使用 `email` 查询 `user_info`。由于模型使用 GORM 软删除，普通查询会自动排除 `deleted_at` 不为空的用户。
3. 调用 `auth.VerifyPassword(user.Password, loginReq.Password)`，内部使用 `bcrypt.CompareHashAndPassword` 校验输入密码和数据库哈希。
4. bcrypt 校验失败时，当前代码还会执行一次旧数据兼容判断：直接比较数据库字段和输入密码。如果两者相同，说明该账号仍保存的是明文密码。
5. 旧明文密码匹配后，立即重新调用 bcrypt 哈希并更新数据库，实现登录时的密码升级；如果明文也不匹配，则返回密码错误。
6. 密码验证成功后调用 `auth.GenerateToken`，JWT claims 中包含用户 `uuid` 和 `is_admin`，有效期为 24 小时。
7. 前端保存返回的 JWT，后续 HTTP 请求通过 `Authorization: Bearer <token>` 发送；WebSocket 握手也携带同一个 token。

#### 三、后续接口如何校验登录身份

登录成功后的业务接口经过 `AuthMiddleware`：

1. 读取 `Authorization` 请求头。
2. 检查格式是否为 `Bearer <token>`。
3. 使用服务端启动时从 `KAMA_JWT_SECRET` 读取的密钥解析 JWT。
4. 验证签名、算法和过期时间。
5. 把 claims 中的 `uuid` 和 `is_admin` 写入 Gin context。
6. 业务控制器从 context 获取当前用户身份，而不是信任请求体中的用户 ID。

JWT 使用 HS256 签名，服务启动时要求密钥长度至少为 32 字节。JWT 是身份凭证，不是密码哈希，不能把 JWT 当作密码存储方案。

#### 四、当前实现的安全边界

- 当前已经使用 bcrypt 处理新注册密码，这是正确的密码存储方向。
- 旧明文兼容逻辑可以帮助历史用户迁移，但它意味着系统在迁移期间仍接受明文数据库字段；应尽快清理并删除这段兼容逻辑。
- 注册控制器中不再打印请求体，避免泄露密码或验证码。
- 登录 Service 会返回用户的 `status`，前端会阻止禁用用户继续进入系统；但更安全的做法是后端在签发 JWT 之前直接拒绝禁用用户，不能只依赖前端判断。
- 密码请求需要通过 HTTPS 传输；当前服务使用 `RunTLS`，生产环境还必须使用可信证书、正确的 TLS 配置，并禁止明文 HTTP 绕过。
- 生产环境应对登录接口增加限流、失败次数控制、验证码或设备风控，防止邮箱密码被暴力尝试。

**面试表达：**

“项目不保存明文密码，新注册用户使用 bcrypt 哈希后存入 `user_info.password`，字段长度为 60。登录时先按邮箱（规范化后）查询用户，再用 `bcrypt.CompareHashAndPassword` 校验输入密码和数据库哈希。校验成功后签发一个包含用户 UUID 和管理员标识的 JWT，后续 HTTP 和 WebSocket 请求都携带 JWT，由中间件验证签名和有效期并把用户身份写入 context。项目目前还保留了旧明文密码的登录迁移逻辑，匹配后会立即升级为 bcrypt；这属于过渡方案，生产环境应清理明文兼容。注册使用邮箱验证码（SMTP 发送，Redis 5 分钟有效，一次性消费），不再依赖手机号短信。”
