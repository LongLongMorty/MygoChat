# KamaChat 面试高频问答

> 聚焦面试实际被问到的 5 个主题：**保序机制、群聊写扩散扇出、Kafka 分流、Redis 的作用、多用户跨服务器顺序与不丢失**。
>
> 每个问题按：**一句话结论 → 机制拆解（带代码位置）→ 取舍边界 → 面试话术 → 追问** 组织。所有行号对应当前 `main` 分支代码。

---

## 通用答题框架

介绍任何机制都按这个骨架说，面试官会觉得你有体系：

1. **先给结论**（一句话点出核心手段）。
2. **分层拆解**（入口 → 处理 → 投递 → 持久化，逐层说谁负责什么）。
3. **讲清取舍**（为什么这么做、代价是什么）。
4. **给出边界**（哪里不保证，诚实加分）。
5. **数据佐证**（压测/监控里能看到的数字）。

## Q1：消息保序机制是怎么做的？

### 一句话结论
**入口给每个会话分配递增序号，`SessionRouter` 按序号重排兜底；跨实例再叠加"同一会话只有一个处理者"（分区/会话亲和）。**

### 机制拆解
1. **入口定序**：消息进 `processLocal` 时，按 `session_id` 取该会话的独立计数器自增，写入信封 `MessageEnvelope.SeqNum`
   （`hybrid_router.go:525-527`，`getOrCreateSessionSeq` 在 `hybrid_router.go:213`）。序号是**每会话从 1 递增**，不是全局序号。
2. **信封随链路走**：channel 和 Kafka 两条路径都传整个信封，序号一路带到消费端。
3. **会话队列重排**：`SessionRouter` 每个会话一个队列 + `nextExpectedSeq`：
   - `seq > 期望`：先进 buffer 缓存（乱序到达）；
   - `seq < 期望`：判定重复，丢弃；
   - `seq == 期望`：处理并推进，再看 buffer 里有没有下一连续序号（`session_router.go:235-291`）。
4. **Kafka 路径天然单写者**：`session_id` 作 Kafka key → 哈希到同一分区 → 消费组内同一消费者，配合信封序号重排。
5. **跨实例**：靠"会话亲和"让同会话固定一个实例处理（见 Q5）。

### 取舍与边界
- 序号是**进程内内存态**：实例重启、空闲会话队列被清理后从 1 重新开始；**跨重启不承诺严格顺序**，历史顺序以 `id/created_at` 为准。
- 乱序 buffer 目前是内存 map，正常乱序窗口很小；若某条序号永久缺失，buffer 可能滞留（空闲清理要求队列和 buffer 都空）——这是可改进点（加最大缓冲/超时逐出）。

### 面试话术
> "保序分两层。第一层是在消息入口按会话分配递增序号，写进信封，channel 和 Kafka 都带着它走。第二层是会话路由器，每个会话一个队列，维护一个期望序号：来的序号大了先缓存，小了当重复丢掉，正好对上就处理并推进，从缓存里续上连续的下一条。这样即使网络导致到达乱序，也会被重排成 FIFO。跨实例时再靠 Kafka 的 session_id 分区或会话亲和，保证同一会话只被一个实例处理。"

### 追问
- **为什么不用时间戳或数据库自增排序？** 时间戳同毫秒难区分且有时钟漂移；DB 自增要落库后才知道，实时投递等不起。序号在入口分配，投递前就能定序。
- **乱序缓存会不会爆？** 正常窗口很小；缺号场景需要补最大缓冲和超时逐出，目前是已知改进项。

## Q2：群聊的写扩散/扇出机制是什么？

### 一句话结论
**一条群消息落库后只构造一份投递体，交给 8 个 worker 的协程池，按群哈希分片广播给群内在线成员——这就是"写扩散"。**

### 机制拆解
1. **触发**：`MessageProcessor` 判断 `ReceiveId` 以 `G` 开头 → `forwardToGroup` → `Fanout.Submit(groupId, messageBack)`。
2. **协程池**：`FanoutExecutor`，8 个 worker × 每 worker 1024 队列（`fanout_executor.go:12-14`）。
3. **分片保序**：`shard()` 用 FNV 哈希把群映射到固定 worker（`fanout_executor.go:68`）——**同一群的扇出任务永远进同一 FIFO 队列串行执行**，群内到达顺序不乱。
4. **非阻塞提交**：队列满直接 `default` 丢弃并计数 `fanoutQueueDrops`（消息已落库，实时推送尽力而为）。
5. **执行**：`fanout()`（`fanout_executor.go:88`）先 `getActiveGroupMemberIDs`（Redis Set 缓存，miss 才查 DB），再交给 `Distributor.Deliver`：本机成员直投，异地成员按实例聚合转发。
6. **回显**：发送方也是群成员，天然包含在广播里。

### 取舍与边界
- **为什么写扩散**：一次写、N 次投递，读时无需关联成员；群规模中等时最简单。代价是成员越多扇出越大。
- 超大人群（万级）写扩散放大严重，应改读扩散（拉取）或分批/合并投递。
- 丢实时推送 ≠ 丢消息：已落库，可拉历史。

### 面试话术
> "群消息先落库，然后只构造一条投递体，提交到扇出协程池。池子有 8 个 worker，按群 ID 哈希分片，同一个群的扇出永远落在同一个 worker 的同一个队列里串行执行，保证群内顺序；不同群并行。worker 取群成员时走 Redis Set 缓存，命中就零 DB 查询，然后把成员分成本机和异地，本机直投、异地按实例聚合转发。队列满了会丢实时任务但会计数，因为消息已经落库，用户重连能拉历史。"

### 追问
- **1 万人大群怎么办？** 写扩散放大严重，改读扩散或分批/合并；本项目已把远程发布从 O(成员数) 收敛到 O(实例数)。
- **扇出的消息丢了算丢吗？** 不算持久丢失，只是实时推送尽力而为。

## Q3：Kafka 分流（背压溢出）是怎么设计的？

### 一句话结论
**Channel 是低延迟主路径；背压检测到 channel 持续高水位后，把消息自动分流到 Kafka 兜底，并且"会话粘滞"避免两条链路乱序。**

### 机制拆解
1. **背压检测**：`BackpressureDetector` 每秒采样 channel 深度；阈值 = `CHANNEL_SIZE * 4/5`（`hybrid_router.go:93`）；持续 5 秒超阈值进入 overflow，低于低水位冷却 10 秒退出（高低水位有滞后，防抖）。
2. **不阻塞分流**：`sendToChannel` 用 `select { case Transmit <- data: ...; default: 走 Kafka }`（`hybrid_router.go:584`）——channel 满立即转 Kafka，发送方不阻塞。
3. **溢出即走 Kafka**：`SendMessage` 判断 overflow 或会话已粘滞 → `ChatWriter`，**以 `session_id` 作 key 保分区顺序**。
4. **会话粘滞**：`sessionRoutedToKafka[sessionId]`（`hybrid_router.go:548/556/624`）——一旦某会话进 Kafka，恢复前不再回切 channel，避免同会话两链路并存导致乱序；另有 5 分钟 TTL 安全清理。
5. **消费**：`consumeKafkaMessages`（`hybrid_router.go:324`）批量 `FetchMessage` → 每消息落库确认（`EnqueueMessagesAndWait`）→ 批量 `CommitMessages`；失败重试，达上限转死信。

### 取舍与边界
- **为什么不直接全用 Kafka**：纯 Kafka 有网络/批量开销，达不到毫秒级 P50；纯 channel 无法削峰、满了只能丢。Hybrid 兼顾低延迟与过载不丢。
- Kafka 溢出是**可靠性兜底**而非性能路径，排空吞吐受单实例单消费者限制（文档实测约 19→30 msg/s）。
- 粘滞是"用一点延迟/复杂度换取顺序确定性"的取舍。

### 面试话术
> "正常负载走内存 channel，毫秒级。背压检测器每秒看 channel 深度，超过容量的五分之四并持续 5 秒就进溢出模式。channel 满的时候用 select+default 立刻把消息转到 Kafka，发送方不会被阻塞。关键是一个会话一旦进了 Kafka 就保持粘滞，恢复前不再回切 channel，否则同一会话两条链路同时走一定乱序。消费端是批量拉取、落库成功才提交 offset，失败重试，超过上限进死信。"

### 追问
- **溢出判定会抖动吗？** 有高/低水位滞后 + 持续窗口 + 冷却窗口三重防抖。
- **Kafka 写失败怎么办？** 新会话可回退 channel；已粘滞会话不回退（保序优先），返回错误让客户端重试。

## Q4：Redis 在项目里起什么作用？

### 一句话结论
**Redis 承担"缓存 + 跨实例协调/路由 + 轻量队列 + 计数"，但它不是持久化真相源——MySQL 才是。**

### 机制拆解（按用途分类）
| 用途 | Key | 说明 |
| --- | --- | --- |
| 在线路由表 | `presence:user:<uuid>` → 实例ID | 分布式定位用户在哪台机 |
| 实例注册 | `chat:instance:<id>`（TTL） | 一致性哈希环发现存活实例 |
| 实例间投递总线 | `chat:deliver:<instanceID>`（Stream） | 消费组 + XACK + pending 重投，跨实例转发 |
| 群成员缓存 | `group_member_set_<groupId>`（Set） | 投递/扇出零 DB 查询，miss 回源 + 变更失效 |
| 会话/历史缓存 | `session_list_*`、`group_session_list_*`、`message_list_*`、`group_messagelist_*` | 读多写少，cache-aside |
| 认证 | `auth_code_email_<email>`、`auth_user_status_<uuid>` | 验证码 5min 一次性、用户状态缓存 |
| 限流 | `ratelimit:<prefix>:<ip>` | `INCR` + `EXPIRE` 固定窗口 |
| 关系/鉴权缓存 | `contact_black_*`、`send_auth_*` | 拉黑、发送权限，变更主动失效 |

**设计原则**：缓存 miss 回源 MySQL；变更"主动失效 + TTL 兜底"；缓存故障尽量不阻塞主链路（如群成员缓存 fail-open 回源 DB，权限校验 fail-closed）。

### 取舍与边界
- 在线连接本身仍在**进程内存**（`map[uuid]*Client`），Redis 只存"路由指针"，避免每次投递多一次网络往返。
- Redis 故障时：单机收发仍可用；跨实例投递/在线定位失效；限流 fail-open。

### 面试话术
> "Redis 在这个项目里不是数据库，是缓存和协调层。一是缓存：群成员 Set、会话历史、邮箱验证码、用户状态、拉黑和发送权限，都是回源 MySQL + 主动失效 + TTL 兜底。二是跨实例协调：presence 表记录用户在哪台机，Redis Stream 做实例间投递总线。三是计数：限流用 INCR+EXPIRE。在线连接本身放进程内存，Redis 只存路由指针，保证本机投递还是内存快路径。"

### 追问
- **缓存一致性怎么保证？** 更新后主动删除/失效 + TTL 兜底；强一致靠 MySQL 唯一约束兜底（如邮箱唯一）。
- **为什么用 Stream 不用 Pub/Sub？** Stream 有消费组、ACK、pending 重投，至少一次；Pub/Sub 是发后不管。

## Q5：很多用户分布在不同服务器，怎么保证顺序到达且不丢失？

### 一句话结论
**顺序靠"单写者 + 序号重排"（跨实例靠会话亲和把同会话固定到一个实例）；不丢靠"先落库后提交 offset + 幂等去重 + 死信 + 至少一次总线"。**

### 顺序部分
1. **核心矛盾**：同会话被两个实例同时处理 → 序号各自独立、冲突乱序。
2. **会话亲和**：`SessionRing` 一致性哈希（每实例 128 虚拟节点）把 `session_id` 稳定映射到某实例（`session_ring.go:72`）；非归属实例把**原始消息**经实例总线转发给归属实例（`hybrid_router.go:499`），由归属实例**单点分配序号并处理**（`processLocal`）。
3. **Kafka 路径**：`session_id` 作 key → 同分区 → 消费组内同消费者，天然单写者。
4. **兜底重排**：`SessionRouter` 按序号缓冲重排（Q1）。

### 不丢失部分
1. **落库边界**：Kafka 消费"拉取 → 处理 → 落库成功 → 才提交 offset"；未提交时进程崩溃，重启重放。
2. **幂等去重**：入口生成稳定 `MsgID`（客户端 `client_msg_id` 派生）；落库以 `message.uuid` 唯一索引 + `ON DUPLICATE KEY UPDATE`（`message_batch.go:182`）——重放不产生重复行、不再整批失败。
3. **死信兜底**：毒消息连续失败达上限 → 转投 `chat_message_dlq` 并提交 offset（`hybrid_router.go:428`），不阻塞分区；转投失败则不提交、继续重试，绝不静默丢。
4. **跨实例投递**：Redis Stream 至少一次 + 接收端 TTL 去重；消息已落库，投递失败可拉历史恢复。
5. **客户端重试**：发送带 `client_msg_id`，服务端据此去重。

### 诚实边界（一定要主动说）
- **channel 常态路径不等待落库**（实时性优先）；要强可靠就走 Kafka 路径。
- **会话亲和 fail-open**：转发失败回退本地处理，可能牺牲该条消息的跨实例顺序换可用性。
- **实例上下线**：一致性哈希减少重映射，但环刷新过渡窗口内可能有顺序瑕疵。
- **Kafka 单副本**（本地 Compose 环境），生产需多副本 + `min.insync.replicas`。
- **序号内存态**：跨重启不承诺严格顺序，历史以 `id/created_at` 为准。

### 面试话术
> "先说说为什么难：同一会话如果被两台机器同时处理，各自的序号计数器会打架，必然乱。所以我们用会话亲和——一致性哈希把每个会话固定映射到一台机器，别的机器收到这个会话的消息就通过 Redis Stream 转发过去，由归属机器单点分配序号、单点处理，这样整个集群里一个会话只有一个写者，顺序就稳了。Kafka 那条线则用 session_id 做 key，同一会话固定一个分区一个消费者。不丢这块：消费端必须落库成功才提交 offset，崩溃重放；消息 ID 在入口就定好，落库用唯一索引加 ON DUPLICATE KEY 幂等，重放不会重复；毒消息超过重试上限进死信，不卡分区。要诚实说明：普通 channel 路径为了低延迟不等落库，强可靠走 Kafka；亲和转发失败会 fail-open 回退本地，可能牺牲这条的顺序。"

### 追问
- **怎么证明不丢不乱？** 压测工具统计 gaps/duplicates、DB 持久化数、Kafka lag；结果 100% 投递、gaps=0、lag 回落 0。
- **两个用户在不同机器同时发同一会话？** 开了亲和都进同一归属实例串行处理；不开亲和各自有序但没有全局总序。
- **扩缩容时顺序怎么办？** 一致性哈希只重映射受影响会话；更严格可用分区所有权迁移，过渡期接受短暂抖动。

## 附：容易被追问翻车、别乱说的点

1. 别说"绝对零丢失"——要区分**实时投递尽力而为**与**持久化不丢**；channel 路径不等落库是已知边界。
2. 别说"分布式已大规模验证"——如实说"设计实现 + 单测，双实例联调建议现场演示"。
3. 别说"Redis 存消息"——消息真相源是 MySQL，Redis 是缓存/总线。
4. 别说"序号全局唯一/全局递增"——是**每会话**递增。
5. 别把 **MsgID（幂等键）** 和 **SeqNum（顺序键）** 混为一谈。
